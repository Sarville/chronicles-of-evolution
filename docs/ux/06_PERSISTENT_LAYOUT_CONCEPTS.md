# Хроники Эволюции — варианты постоянной компоновки

**Документ:** DS-08 / Global Layout Approval  
**Статус:** prepared for user review  
**Область:** варианты постоянного desktop/mobile shell перед production-генерацией диорам и UI sheet  
**Входы:** `00_UX_PRINCIPLES.md`, `01_SCREEN_MAP.md`, `02_MOBILE_WIREFRAMES.md`, `03_DESKTOP_WIREFRAMES.md`, `../art/07_CONCEPT_SCREEN_AND_ASSET_PIPELINE.md`

---

# 1. Назначение

Этот документ готовит выбор постоянной компоновки для Timeline #1. После выбора desktop/mobile shell считается стабильным для всех эпохальных блоков `B00–B05`; дальше меняются диорама, содержимое панелей, milestone overlays и кризисные состояния, но не базовые места управления.

Варианты не меняют DS-06 UX contract:

- диорама остаётся главным surface;
- мобильная версия остаётся mobile-first, а не сжатым desktop;
- ресурсы и системы появляются только после соответствующих unlock;
- в обычной игре всегда видны текущая цель, главное действие или следующий понятный шаг;
- cinematic/milestone/ending surfaces могут временно перекрывать shell, но не становятся новым постоянным layout.

# 2. Общие постоянные зоны

## Desktop, `1366 × 768` baseline

Постоянные зоны, которые должны быть решены в выбранном варианте:

| Зона | Роль | Требование |
| --- | --- | --- |
| `STATUS_STRIP` | эра, время, 1 главный фазовый сигнал | не превращается в строку всех ресурсов |
| `GOAL_AREA` | текущая цель, прогресс, primary action | остаётся доступной даже при открытой правой панели |
| `DIORAMA_STAGE` | живая сцена мира | крупнейшая область в `SCR_WORLD` и `SCR_CRISIS` |
| `SYSTEM_AREA` | «Эволюция», работы, здания, энергия, хроника, события | может быть постоянной панелью или раскрываемым фокусом |
| `FEEDBACK_AREA` | короткие сообщения Архива, recent feedback | не заменяет «Хронику» и не копит все тики |

На desktop нельзя добавлять новые правила игры ради заполнения ширины. Дополнительное место получает диорама, preview последствий, readable spacing и сравнение текущих вариантов.

## Mobile, `360 × 800` baseline

Постоянные зоны:

| Зона | Роль | Требование |
| --- | --- | --- |
| `STATUS_STRIP` | эра, время, 1-2 compact signals | не более трёх индикаторов |
| `DIORAMA_STAGE` | главный вид мира | в обычной игре занимает смысловой центр экрана |
| `GOAL_CARD` | ближайшая цель и прогресс | над нижним действием, не спрятана в sheet |
| `ACTION_DOCK` | primary action и 2-3 контекстных входа | touch targets не меньше 44 px |
| `BOTTOM_SHEET` | подробности, решения, списки | имеет collapsed / half / full состояния |

Mobile layout не должен требовать hover, точного попадания в мелкие строки или постоянного переключения между полноценными экранами.

# 3. Desktop-варианты

## D-A — Diorama Dominant

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ STATUS: эра / время / главный сигнал                                      │
├──────────────┬─────────────────────────────────────────────────────────────┤
│ GOAL +       │                                                             │
│ RESOURCES    │                                                             │
│ PRIMARY CTA  │                    DIORAMA_STAGE                            │
│              │                                                             │
│ SYSTEM TABS  │                                                             │
├──────────────┴─────────────────────────────────────────────────────────────┤
│ FEEDBACK / ARCHIVE WHISPER                                                 │
└────────────────────────────────────────────────────────────────────────────┘
```

**Смысл:** максимум пространства отдаётся миру. Системы раскрываются из левой панели или временным правым фокусом.

**Сильные стороны:**

- лучше всего подчёркивает «диорама прежде всего»;
- хорошо работает для ранней биологии, milestone-переходов, Ash-derived ending;
- меньше риска, что игра станет spreadsheet-like.

**Риски:**

- работы/здания и AP-адаптации могут требовать дополнительного раскрытия;
- на поздних стадиях нужно аккуратно проектировать быстрый доступ к системам.

**Лучше всего подходит, если:** главная цель production — эмоционально сильная диорама и минимальный интерфейс.

## D-B — Balanced Control

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ STATUS: эра / время / главный сигнал                                      │
├──────────────┬──────────────────────────────────────────┬─────────────────┤
│ GOAL +       │                                          │ SYSTEM_AREA     │
│ RESOURCES    │                                          │ фаза / событие  │
│ PRIMARY CTA  │              DIORAMA_STAGE               │ list / preview  │
│              │                                          │ action details  │
│ CONTEXT      │                                          │                 │
├──────────────┴──────────────────────────────────────────┴─────────────────┤
│ FEEDBACK / ARCHIVE WHISPER                                                 │
└────────────────────────────────────────────────────────────────────────────┘
```

**Смысл:** desktop использует две постоянные панели, но диорама остаётся центральной и крупнейшей областью.

**Сильные стороны:**

- самый устойчивый вариант для всей Timeline #1;
- правая панель естественно принимает «Эволюцию», работы, здания, энергию, события и кризис;
- совпадает с текущим DS-06 desktop wireframe.

**Риски:**

- требует строгой ширины панелей, иначе мир начнёт выглядеть зажатым;
- на mobile нужен отдельный, а не буквальный перенос.

**Лучше всего подходит, если:** нужен production-safe default для игры с растущей системной плотностью.

## D-C — System Focus

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ STATUS + compact resources                                                 │
├──────────────────────────────────────┬─────────────────────────────────────┤
│                                      │ GOAL / SYSTEM_AREA                  │
│                                      │ current task                        │
│            DIORAMA_STAGE             │ resources                           │
│                                      │ evolution / jobs / event details    │
│                                      │ primary action                      │
├──────────────────────────────────────┴─────────────────────────────────────┤
│ FEEDBACK / CHRONICLE SNAPSHOT                                              │
└────────────────────────────────────────────────────────────────────────────┘
```

**Смысл:** правая рабочая область крупнее и объединяет цель, ресурсы и текущую систему. Левая отдельная панель отсутствует.

**Сильные стороны:**

- хорошо читаются работы, здания, энергетические решения и crisis event stack;
- меньше разнесённости внимания между двумя боковыми панелями;
- удобен для мыши и клавиатуры.

**Риски:**

- мир может стать иллюстрацией рядом с интерфейсом;
- ранние стадии будут выглядеть чрезмерно системными;
- слабее наследует mobile-first порядок, где цель и действие живут снизу.

**Лучше всего подходит, если:** приоритет — плотное управление и частое сравнение системных вариантов.

## D-D — Adaptive Compact

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ STATUS: эра / сигнал                                      [tabs collapsed] │
├──────────────┬─────────────────────────────────────────────────────────────┤
│ GOAL         │                                                             │
│ PRIMARY CTA  │                    DIORAMA_STAGE                            │
│ RESOURCES    │                                                             │
│              │                                                             │
│ [SYSTEM]     │                                                             │
└──────────────┴─────────────────────────────────────────────────────────────┘
```

**Смысл:** shell проектируется вокруг явных collapsed states. Правая панель не постоянная; она открывается поверх части диорамы только когда нужна.

**Сильные стороны:**

- хорошо переносится на tablet и narrow desktop;
- даёт сильную преемственность с mobile bottom-sheet логикой;
- снижает постоянную визуальную нагрузку.

**Риски:**

- на широком desktop часть потенциала экрана остаётся неиспользованной;
- игроку нужно чаще открывать системный фокус;
- поздние стадии могут казаться менее оперативными.

**Лучше всего подходит, если:** важнее адаптивность и консольная/планшетная чистота, чем максимальная desktop-плотность.

# 4. Mobile-варианты

## M-A — Classic Bottom Dock

```text
┌──────────────────────────────────┐
│ STATUS                           │
├──────────────────────────────────┤
│                                  │
│          DIORAMA_STAGE           │
│                                  │
├──────────────────────────────────┤
│ GOAL_CARD                        │
│ progress / hint                  │
├──────────────────────────────────┤
│ ACTION_DOCK: tabs + primary CTA  │
└──────────────────────────────────┘
```

**Смысл:** текущий DS-06 mobile default. Цель и действие живут внизу, подробности открываются bottom sheet.

**Сильные стороны:**

- лучше всего поддерживает игру одной рукой;
- ясно разделяет мир, цель и действие;
- устойчиво для всех фаз от РНК до кризиса.

**Риски:**

- нижняя зона может стать плотной в цивилизационной фазе;
- нужно дисциплинированно ограничивать число постоянных входов.

**Лучше всего подходит, если:** нужен самый надёжный mobile-first shell.

## M-B — Floating Goal Over Diorama

```text
┌──────────────────────────────────┐
│ STATUS                           │
├──────────────────────────────────┤
│                                  │
│   DIORAMA_STAGE                  │
│        ┌────────────────────┐    │
│        │ floating GOAL_CARD │    │
│        └────────────────────┘    │
├──────────────────────────────────┤
│ ACTION_DOCK / primary CTA        │
└──────────────────────────────────┘
```

**Смысл:** карточка цели частично живёт поверх диорамы, чтобы нижний dock оставался ниже и проще.

**Сильные стороны:**

- даёт больше места нижним действиям;
- цель ощущается связанной с миром;
- хорошо для событий, где выбор привязан к объекту диорамы.

**Риски:**

- высокий риск перекрытия важных объектов диорамы;
- требует строгих safe zones для каждой эпохи;
- на маленьких экранах цель может давить на сцену.

**Лучше всего подходит, если:** production готов постоянно проверять occlusion в каждой диораме.

## M-C — Sheet-First Control

```text
┌──────────────────────────────────┐
│ STATUS                           │
├──────────────────────────────────┤
│                                  │
│          DIORAMA_STAGE           │
│                                  │
├──────────────────────────────────┤
│ COLLAPSED SHEET: goal + tabs     │
│ drag → half / full system view   │
└──────────────────────────────────┘
```

**Смысл:** нижний sheet является постоянной управляющей поверхностью. Goal card, tabs и CTA находятся внутри него.

**Сильные стороны:**

- отлично масштабируется к работам, зданиям, хронике и событиям;
- один понятный жест раскрытия;
- сильная преемственность с mobile app patterns.

**Риски:**

- в collapsed состоянии цель может быть слишком сжатой;
- sheet начинает конкурировать с диорамой;
- игрок может чаще смотреть в интерфейс, чем в мир.

**Лучше всего подходит, если:** приоритет — системная читаемость на mobile.

## M-D — Split Focus

```text
┌──────────────────────────────────┐
│ STATUS                           │
├──────────────────────────────────┤
│          DIORAMA_STAGE           │
│          compact but stable      │
├──────────────────────────────────┤
│ GOAL_CARD                        │
├──────────────────────────────────┤
│ SYSTEM_PREVIEW / tabs            │
├──────────────────────────────────┤
│ PRIMARY CTA                      │
└──────────────────────────────────┘
```

**Смысл:** нижняя половина сильнее структурирована: цель, системный preview и главное действие всегда имеют отдельные строки.

**Сильные стороны:**

- очень ясная иерархия действий;
- меньше скрытых деталей в ранних стадиях;
- удобно для tutorial hints и first-session recovery.

**Риски:**

- диорама теряет высоту, особенно на 320 px ширины;
- поздние события могут требовать full sheet чаще;
- опасность ощущения static dashboard.

**Лучше всего подходит, если:** главное — максимальная ясность следующего действия для первого прохождения.

# 5. Рекомендованный short list

## Рекомендация для выбора

Основной кандидат:

- **Desktop: D-B Balanced Control**
- **Mobile: M-A Classic Bottom Dock**

Почему:

- это самый прямой наследник принятых DS-06 вайрфреймов;
- он выдерживает полный диапазон Timeline #1: ранняя биология, AP, работы/здания, энергия, кризис, Архив;
- он не требует постоянных bespoke safe zones для floating goal;
- desktop получает рабочую правую панель, а mobile сохраняет управление одной рукой.

Возможный гибрид:

- взять **D-B** как desktop shell;
- взять **M-A** как baseline;
- разрешить **M-C sheet-first state** только для раскрытых системных листов, а не как постоянное collapsed состояние;
- использовать **D-A/D-D** как временное cinematic simplification для milestone, ending и Archive memory.

## Не рекомендовано как основной путь

- **D-C + M-C**: слишком рано уводит игру в системную панель и ослабляет диораму как главный контекст.
- **D-A + M-B**: очень красиво для concept screens, но дорого в production из-за постоянной проверки перекрытий и риска спрятать цель/действие.
- **D-D + M-D**: чисто и адаптивно, но может сделать игру слишком компактной и утилитарной для мира, который должен расти на глазах.

# 6. Критерии выбора

Выбранная компоновка должна получить ответы:

1. Где живёт текущая цель в обычной игре?
2. Где живёт главное действие, когда система не требует подробного листа?
3. Как раскрывается «Эволюция» после `PB03`, а AP после `PB09`?
4. Где живут работы/здания после `PB17`?
5. Как появляется Power после `PB21`, не занимая место раньше?
6. Как кризис после `PB25` сжимает обычный интерфейс вокруг World Tension?
7. Какие зоны диорамы нельзя закрывать UI на desktop и mobile?
8. Какие элементы можно временно скрывать в milestone/ending, а какие возвращаются в `SCR_WORLD`?

После выбора нужно зафиксировать:

- выбранный desktop shell;
- выбранный mobile shell;
- допустимые temporary states;
- safe zones для диорам;
- правила panel opacity/contrast поверх art;
- rejection rules для future shell previews.

---

# 7. Решение Для Ревью

На ревью достаточно выбрать одно из:

| Decision | Desktop | Mobile | Notes |
| --- | --- | --- | --- |
| `LAYOUT_A` | D-A | M-A или M-B | максимальная диорама, больше production-risk |
| `LAYOUT_B` | D-B | M-A | recommended balanced default |
| `LAYOUT_C` | D-C | M-C | system-readable, но менее diorama-first |
| `LAYOUT_D` | D-D | M-A или M-D | adaptive/compact, осторожнее с поздними фазами |
| `LAYOUT_HYBRID` | D-B + cinematic D-A/D-D states | M-A + expanded M-C sheets | recommended hybrid если нужен гибкий production contract |

До выбора shell нельзя начинать `B00_ORIGIN_CELL` production concepts как финальный pipeline. Можно делать только rough mood tests, не претендующие на утверждение постоянной компоновки.
