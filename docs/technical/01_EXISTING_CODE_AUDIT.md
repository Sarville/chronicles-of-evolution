# Аудит существующего кода

Дата: 2026-09-15  
Область: текущее состояние репозитория `chronicles-of-evolution` без изменений игрового кода, дизайна или архитектуры.

## Краткий вывод

Это зрелая браузерная incremental-игра на vanilla ES-модулях, собранных esbuild в один клиентский bundle. Архитектура практична для контентно насыщенной игры: единое сериализуемое состояние `global`, декларации контента рядом с логикой доменов и рендер интерфейса через jQuery + Vue 2/Buefy. Основной компромисс — слабые границы между симуляцией, состоянием и UI: крупные доменные файлы одновременно определяют действия, изменяют `global`, создают DOM и рассчитывают отображаемые значения.

Критических дефектов в рамках статического чтения не выявлено. Наиболее значимые технические риски для последующей работы: единственное локальное сохранение без обработки ошибок/контроля размера, отсутствие тестов, очень крупные модули и отсутствие платформенной абстракции. Ни один из этих пунктов не требует немедленного большого рефакторинга.

## Игровой цикл

### Запуск

1. `src/vars.js:82-97` синхронно читает ключ `evolved` из `localStorage`, распаковывает его LZString и заменяет начальный `global`; при отсутствии данных создаётся минимальная новая игра.
2. `src/main.js` инициализирует интерфейс (`index()`, `mainVue()`), модели работ/ресурсов, вкладки, очереди и power grid; видимые зоны строятся по текущему состоянию (`src/main.js:283-296`).
3. `src/main.js:865-876` создаёт Web Worker `evolve/evolve.js`, который служит точным таймером и возвращает в главный поток число пропущенных периодов. Вся игровая мутация остаётся в главном потоке.

### Частоты и порядок

`loopTimers()` задаёт базовый fast tick 250 мс, middle tick 1 с и long tick 5 с (`src/functions.js:145-171`). Признаки slow/hyper меняют длительность периода, а накопленное offline/accelerated time временно удваивает скорость.

`execGameLoops()` ограничивает catch-up одним реальным минутным окном — максимум 12 игровых дней — и для каждого периода исполняет порядок `fastLoop → midLoop (раз в 4) → callbacks → longLoop (раз в 20)` (`src/main.js:841-863`). Это хороший инвариант: постоянные результаты callback успевают сохраниться в long loop.

Worker компенсирует дрейф таймеров, а при большой задержке сообщает несколько периодов одним сообщением (`evolve/evolve.js:28-65`). Ограничение catch-up защищает UI от длительного блокирования, но означает, что игра не моделирует всё время простоя буквально; вместо этого применяется ограниченное accelerated time (`src/functions.js:174-205`).

### Что делают уровни цикла

- `fastLoop` пересчитывает глобальные мультипликаторы, производство, расход, лимиты, статусы и отображаемые breakdown; он является главным центром экономики (`src/main.js:882+`).
- `midLoop` обслуживает более редкие производственные, боевые, исследовательские и очередные процессы.
- `longLoop` обслуживает календарь/события/долгие состояния, приводит UI к актуальному виду, снимает временные буферы, сохраняет игру и управляет ускорением (`src/main.js:11531+`, сохранение `12810-12853`).

## Экономика и production formulas

### Модель ресурсов

Ресурс — запись в `global.resource[name]` с как минимум `amount`, `max`, `rate`, `delta`, `diff`, `display`, `value`, `stackable`, storage и торговыми полями. Инициализация и UI-шаблон живут в одной функции `loadResource()` (`src/resources.js:773-840`). `delta` накапливает изменение за тик, а `diff` рассчитывается как наблюдаемая скорость для интерфейса.

Каноническое изменение ресурса — `modRes()` (`src/functions.js:680+`); стоимость списывается централизованно через `payCosts()` после `checkCosts()` (`src/actions.js:7532-7564`). Это две наиболее безопасные точки для небольших правил, которые должны работать в нескольких доменах.

### Где лежат формулы

- Базовые значения и рыночные параметры: `resource_values`, `tradeRatio`, `atomic_mass`, `supplyValue` в `src/resources.js:13-175`.
- Профессии, scaling работников и производительность ферм/крафтеров: `src/jobs.js`.
- Частные производственные формулы построек и кораблей: один `switch` `production(id, val, wiki)` в `src/prod.js:26+`. Он учитывает технологии, биом, геологию, форму правления, traits и режимы игры.
- Стоимость конкретных технологий/построек и их callbacks: декларация `actions` в `src/actions.js:21+`, а технологические декларации — `src/tech.js`.
- Сквозные модификаторы цены: `adjustCosts()` последовательно оборачивает функции стоимости правилами challenges/traits/tech (`src/functions.js:1759-1785`).
- Энергия и производство/потребление построек: `src/industry.js` и `gridDefs()`; актуальная сетка восстанавливается при загрузке и проверяется long loop.

Такое размещение хорошо подходит для точечной настройки контента, но полный итоговый расчёт распределён: базовая формула может быть в `prod.js`, глобальный multiplier — в `main.js`, а стоимость — в `actions.js` + `functions.js`. Перед балансными изменениями стоит трассировать все три слоя и сверять UI breakdown, а не менять одно число изолированно.

### Детерминизм и события

Есть stateful-псевдослучайность `seededRandom()` с `seed`/`warseed`, сохраняемыми в `global` (`src/vars.js:71-80`), но также используется `Math.rand()` на `Math.random()` (`src/vars.js:65-67`). Поэтому игра не является полностью воспроизводимой по одному save seed: часть событий сознательно случайна. Major/minor events выбираются в long loop и тоже мутируют сохранённое состояние (`src/main.js:12721-12760`).

## Save и данные

### Формат и жизненный цикл

Основной save — одна JSON-структура `global`, сжатая `LZString.compressToUTF16` в `localStorage['evolved']`. Автосохранение выполняется раз в long loop, то есть примерно раз в 5 секунд до модификаторов (`src/main.js:12821-12825`). Экспорт — base64-вариант того же JSON (`src/functions.js:207-213`); импорт валидирует только несколько верхнеуровневых полей и перезагружает страницу (`src/functions.js:215-256`).

Перед несколькими необратимыми переходами создаётся локальная резервная копия `evolveBak` (например `src/resets.js:10`, `src/space.js:7502`); в settings есть восстановление этой копии (`src/index.js`, метод `restoreGame`). Soft/hard reset корректно останавливают worker, а hard reset удаляет только основной ключ (`src/vars.js:2431-2442`).

### Совместимость

Миграции применяются сразу после загрузки в `src/vars.js` через большое число проверок версии и отсутствующих полей. `convertVersion()` нормализует семантическую версию к числу (`src/vars.js:2040-2045`). Это обеспечивает совместимость сохранений, но миграции не выделены в версионированный pipeline и не покрыты автоматическими тестами.

### Риски и малые улучшения на будущее

1. Загрузка `JSON.parse(LZString.decompressFromUTF16(...))` не окружена `try/catch` (`src/vars.js:83-97`). Повреждённый или вручную изменённый save может остановить старт игры вместо предложения восстановить backup/export.
2. Сохранение единым ключом зависит от browser quota; нет проверки `setItem`, контроля размера или ротации копий. Для текущей локальной web-версии это приемлемо, но это первое место для усиления надёжности без смены экономики.
3. Multi-tab detection только предупреждает через событие `storage` (`src/main.js:47-52`); конфликт двух одновременно открытых вкладок не разрешается.
4. Слой платформенного/cloud save отсутствует, поэтому перенос прогресса между устройствами и аккаунтами не поддерживается.

## Границы UI

`index.html` — статический shell. Он загружает jQuery, Vue 2, Buefy, Popper, Sortable и Chart.js через CDN, LZString локально и затем `evolve/main.js` как ES module (`index.html:10-21`). В build bundle попадают исходники из `src/main.js`; CSS компилируется из `src/evolve.less`.

UI строится динамически: доменные модули создают jQuery-элементы со строковыми Vue templates, затем `vBind()` создаёт/force-update/destroy Vue instances (`src/functions.js:1112-1148`). Примеры: ресурсы в `src/resources.js:835+`, действия в `src/actions.js:6202-6278`, вакансии в `src/jobs.js`. `mainVue()` обслуживает settings, import/export и переключения высокого уровня (`src/index.js:26+`).

Граница фактически выглядит так:

```text
пользовательский input / Vue handler
        → action/job/resource method
        → global (сразу меняется)
        → fast/mid/long loop пересчитывает derived state
        → jQuery/Vue redraw, popover и breakdown
```

Плюсы: быстрый путь от контентной декларации к экрану, высокая гибкость в динамически открываемых разделах, без тяжёлого виртуального DOM. Минусы: одно действие может смешивать DOM, бизнес-правила и запись в `global`; невидимые зависимости на CSS id/class и `__vue__` усложняют unit-тесты и замену UI. Следующий UI-изменение следует проводить внутри одной зоны/рендера, не меняя при этом формат состояния или расчёты.

## Платформенная интеграция

### Текущий факт

Проверены исходники, HTML, `package.json`, дерево конфигураций и deployment scripts. Признаков `YaGames`, `ysdk`, `vkBridge`, `VKWebApp`, Yandex/VK build flags, manifest, backend/ops или CI нет. Проект сегодня — self-contained статический web build. `npm run deploy` собирает `dist` и публикует его через `gh-pages` (`package.json`).

Из внешнего окружения используются:

- Google Analytics (`gtag`) в `index.html:56-61`, с безопасно подавляемыми ошибками при отправке `tagEvent()` (`src/functions.js:658-664`);
- проверка версии по upstream `https://pmotschmann.github.io/Evolve/package.json` раз в 15 минут (`src/main.js:12977-12988`);
- CDN-зависимости интерфейса из `unpkg.com` и Google Fonts.

### Статус по Yandex Games / VK Mini Apps чек-листу

Это не означает ошибку текущей web-версии — интеграция не заявлена. Если публикация на платформах станет задачей, требуются отдельные малые этапы.

| Раздел | Статус | Наблюдение |
| --- | --- | --- |
| Целевые build variants | ❌ | Нет флагов или platform wrapper. |
| SDK, ready/loading, язык платформы | ❌ | Нет Yandex/VK SDK и сигналов готовности. |
| Banner/interstitial/rewarded ads | ❌ | Рекламных API и флага disable-ads нет. |
| In-app purchases | ❌ | Нет product catalogue, purchase flow или VK ledger/backend. |
| Защита VK iframe | ❌ | Нет server-side валидации launch signature; статический сайт доступен напрямую. |
| Auth и cloud save | ❌ | Только `localStorage`; нет аккаунта, Yandex player storage или VK storage. |
| Platform deploy layout | ❌ | Есть GitHub Pages deploy, но нет Yandex ZIP/VK HTTPS iframe конфигурации. |
| Кабинеты, цены, callback, витрина | ❔ | Нельзя проверить из кода; не обнаружены project-local настройки. |

Особое ограничение для Yandex: текущий HTML использует относительные пути для локальных ассетов, что полезно для CDN-подкаталога, но Yandex SDK отсутствует. Для VK понадобится не только клиентская проверка query params, а server/edge-проверка подписи launch params; её нельзя считать задачей фронтенд-рефакторинга.

## Переиспользуемые engine-подсистемы

Следующие части уже обладают достаточно чёткой логической границей и пригодны для повторного применения или постепенного извлечения без переписывания игры:

- цикл и низкодрифтовый worker: `gameLoop`, `loopTimers`, `execGameLoops`, `evolve/evolve.js`;
- модель ресурса и безопасная оплата: `loadResource`, `modRes`, `checkCosts`, `payCosts`;
- декларативная система действий: `actions`, `setAction`, `checkTechRequirements`, `adjustCosts`;
- очереди строительства/исследований и callback queue: `src/functions.js` + `src/actions.js`;
- power grid: `gridDefs`, `powerGrid`, `gridEnabled`, `setPowerGrid`;
- seeded random и генерация планет: `seededRandom`, `genPlanets`;
- локализация: `loc()` и JSON string packs (`src/locale.js`, `strings/`);
- presentation helpers: `vBind`, popover, `sizeApproximation`, SVG icon helpers.

Они пока не изолированы от `global`, jQuery или конкретных имен ресурсов, поэтому это «внутренние reusable pieces», а не готовый независимый engine package. Извлекать их отдельно имеет смысл только при реальной потребности во втором проекте/режиме или при появлении тестов вокруг конкретной подсистемы.

## Приоритеты без большого refactor

1. **P1 — надёжность save.** Добавить малую защиту чтения/записи: `try/catch`, понятный путь к `evolveBak`/import при повреждении и телеметрию только факта ошибки. Не менять формат сохранения без отдельной миграции.
2. **P1 — минимальный regression harness.** До изменения формул завести фиксированные экспортированные saves и smoke-проверку загрузки, одного long loop и ключевых migrations. Сейчас в репозитории нет test suite.
3. **P2 — карта формул для конкретных сценариев.** Для первого 120-минутного контента поддерживать небольшой список «source of truth»: действие → cost → `adjustCosts` → production → UI breakdown. Это документационная дисциплина, не миграция framework.
4. **P2 — platform boundary только по запросу публикации.** Когда будут определены Yandex, VK или обе цели, добавить маленький `platform` adapter поверх save/ads/payments, не встраивая SDK-вызовы в `main.js` и доменные модули.
5. **P3 — постепенное уменьшение coupling.** При касании конкретного action/renderer отделять чистую расчётную функцию от DOM-отрисовки и добавлять ей тест. Не переносить массово существующие декларации.
