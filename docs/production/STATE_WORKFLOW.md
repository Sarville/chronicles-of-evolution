# Хроники Эволюции — state workflow

`docs/PROJECT_STATE.yaml` — единственный канонический источник текущего состояния проектирования и реализации.

`docs/TODO.md` — человекочитаемое представление ближайшей работы. Если `TODO.md` расходится с `PROJECT_STATE.yaml`, верен `PROJECT_STATE.yaml`.

---

## 1. Жизненный цикл дизайн-сессии

Каждая сессия имеет ID `DS-XX` из `DESIGN_SESSION_PLAN.md`.

### Старт

Перед началом новой сессии:

1. прочитать `PROJECT_STATE.yaml`;
2. убедиться, что session имеет `ready`;
3. прочитать только её dependencies/inputs;
4. проверить open decisions;
5. не начинать документы следующего блока.

### Работа

ChatGPT формирует весь связанный пакет текущей сессии в рамках одного чата.

В процессе допустимы промежуточные варианты, но в репозиторий как канонический результат попадает только версия после пользовательской проверки.

### Review

После подготовки блока пользователь:

- принимает;
- просит изменения;
- либо откладывает отдельные решения.

До принятия session имеет `review`, а её документы не считаются стабильными входами для Codex.

### Завершение

После одобрения обязательно одним логическим обновлением:

1. сохранить/обновить документы сессии;
2. поменять session status на `done`;
3. разблокировать зависимые sessions (`blocked` -> `ready`, если все dependencies done);
4. установить следующий `current_session`;
5. обновить `documentation` statuses;
6. обновить `TODO.md`;
7. добавить записи в `DECISIONS.md`, если появились новые решения;
8. при необходимости обновить `GLOSSARY.md`;
9. commit/push.

Только после этого рекомендуется начинать новый чат.

## 2. Статусы

### `todo`
Работа определена, но dependencies ещё не проверены.

### `ready`
Все зависимости выполнены; блок можно начинать.

### `active`
Сейчас выполняется.

### `review`
Черновик готов, ожидается пользовательская проверка.

### `done`
Пользователь принял блок, изменения зафиксированы в repo.

### `blocked`
Есть невыполненная dependency или unresolved decision, без которого работа некорректна.

### `paused`
Работа сознательно остановлена, хотя технически могла бы продолжаться.

### `partial`
Часть checklist сделана, но gate не закрыт. Используется прежде всего для implementation iteration.

---

## 3. Кто обновляет state

### ChatGPT
Может обновлять:
- `design.*`;
- `documentation.*`;
- `next_action`;
- `open_decisions` после пользовательского решения;
- implementation status только как организационный gate (`paused`, `resume_gate`), но не заявлять кодовую задачу выполненной без проверки результата Codex.

### Codex
После implementation iteration обновляет:
- `implementation.iterations.*`;
- implementation blockers;
- технические результаты/риски;
- `TODO.md` implementation section.

Codex не переводит design session в `done` и не меняет канонические product decisions самостоятельно.

### Пользователь
Approval пользователя закрывает review gate дизайн-сессии и продуктовые решения.

---

## 4. TODO synchronization

`TODO.md` не должен дублировать весь roadmap.

Он содержит только:
- текущую фазу;
- активную/следующую design session;
- её конкретные deliverables;
- текущее состояние Codex;
- ближайшие blockers;
- 1–2 следующих готовых действия.

Большие списки будущих design sessions живут в `DESIGN_SESSION_PLAN.md`, implementation iterations — в `IMPLEMENTATION_ITERATION_PLAN.md`.

При каждом accepted session обновление `PROJECT_STATE.yaml` и `TODO.md` выполняется в одном commit/push cycle.

## 5. Параллельная работа

До DS-03 Codex implementation остаётся на паузе, кроме безопасных исследовательских/измерительных задач.

После DS-03 допустима параллельная работа.

### Правило владения файлами

Чтобы минимизировать конфликты:

- ChatGPT/design не изменяет исходный код приложения;
- Codex не изменяет канонический GDD/scenario/UX/art/audio без отдельного задания;
- оба могут обновлять `PROJECT_STATE.yaml` и `TODO.md`, но только свои секции;
- изменения state делаются после проверки актуального HEAD.

### Ветки при реальной параллельности

Если два агента работают одновременно, рекомендуется использовать отдельные ветки:

```text
docs/ds-05-timeline-script
impl/i01-domain-adapter
```

После review изменения сливаются в `master`, затем `PROJECT_STATE.yaml` пересчитывается относительно нового HEAD.

Если активен только один поток, допустим прямой commit в `master`.

---

## 6. Commit conventions

Рекомендуемые сообщения:

```text
docs(DS-01): add civilization gameplay contract
docs(DS-05): finalize Timeline 1 narrative
state: advance design to DS-06
impl(I01): add domain adapter foundation
```

Для завершения сессии предпочтительно один логический commit, включающий документы + state + TODO + decisions.

---

## 7. Новый чат

Новый чат начинается короткой командой вида:

> Продолжаем Хроники Эволюции. Открой GitHub, прочитай `docs/PROJECT_STATE.yaml` и выполни текущую design session.

Этого должно быть достаточно: текущий блок, dependencies и source files определяются из repo.

---

## 8. Если найдено противоречие

Не исправлять молча.

1. определить конфликтующие источники;
2. проверить `DECISIONS.md` и source-of-truth hierarchy;
3. если решение уже существует — привести новый документ к нему;
4. если решения нет — вынести вопрос пользователю;
5. после решения обновить `DECISIONS.md`;
6. только затем закрывать session.

---

## 9. Если Codex опередил документацию

Код не становится источником product truth.

Если реализация содержит решение, которого нет в accepted docs:

- либо решение принимается и записывается в `DECISIONS.md`/GDD;
- либо Codex получает задачу привести реализацию к документации.

Нельзя автоматически менять GDD только потому, что код уже написан иначе.
